## 为什么不是单 AES 或单 RSA

- **AES（对称）**：快，但密钥分发是死结——前端把密钥写在 JS 里，等于没加密
- **RSA（非对称）**：无密钥分发问题，但慢，且对明文长度有强限制（2048 位 RSA 只能加密 ~245 字节）

工业方案是**混合加密**：

1. 前端随机生成一次性 AES 密钥
2. 用 AES 加密业务数据（任意长度，快）
3. 用后端的 RSA 公钥加密这个 AES 密钥
4. 把 `(密文, 加密后的 AES 密钥)` 一起发给后端
5. 后端用 RSA 私钥解出 AES 密钥，再用它解密业务数据

## Web Crypto API

浏览器原生 `window.crypto.subtle` 提供 AES-GCM 和 RSA-OAEP。比 CryptoJS 快 10 倍以上，且经过审计。

```ts
const key = await crypto.subtle.generateKey(
  { name: 'AES-GCM', length: 256 },
  true,
  ['encrypt', 'decrypt'],
);

const iv = crypto.getRandomValues(new Uint8Array(12));
const cipher = await crypto.subtle.encrypt(
  { name: 'AES-GCM', iv },
  key,
  new TextEncoder().encode(JSON.stringify(payload)),
);
```

## 实战中踩的坑

### 坑 1：RSA-OAEP 默认哈希不一致

Web Crypto 的 `RSA-OAEP` **不显式指定 hash 时，不同浏览器默认值不一样**。后端 Java 默认是 SHA-1，前端 Chrome 也默认 SHA-1，但 Safari 是 SHA-256。

修复：显式指定。

```ts
crypto.subtle.encrypt(
  { name: 'RSA-OAEP', hash: 'SHA-256' },  // 必须显式
  publicKey,
  aesKeyRaw,
);
```

### 坑 2：PEM 公钥的解析

后端给的公钥是这种格式：

```
-----BEGIN PUBLIC KEY-----
MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
-----END PUBLIC KEY-----
```

Web Crypto 不能直接用，要先 base64 解码成 ArrayBuffer：

```ts
function pemToBuffer(pem: string): ArrayBuffer {
  const b64 = pem
    .replace(/-----[A-Z ]+-----/g, '')
    .replace(/\s/g, '');
  const binary = atob(b64);
  const buf = new Uint8Array(binary.length);
  for (let i = 0; i < binary.length; i++) buf[i] = binary.charCodeAt(i);
  return buf.buffer;
}
```

### 坑 3：int64 精度丢失

加密前的 payload 里如果有 int64 ID（比如 `1756382948364723`），`JSON.stringify` 会把它转成 number，丢精度。解决方案：json-bigint。

## 评标系统的落地

投标文件里有大量敏感信息（投标价、技术方案）。我们这套方案做了三层：

| 层 | 时机 | 算法 |
|---|---|---|
| 传输层 | HTTPS | TLS 1.3 |
| 业务层 | 敏感字段加密 | AES-GCM + RSA-OAEP |
| 文件层 | 大文件分片加密 | 每片 AES-GCM + 上传时签名 |
